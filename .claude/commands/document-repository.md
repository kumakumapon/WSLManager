# リポジトリ文書化プロンプト

対象リポジトリの現行実装を根拠に、初見の開発者・保守担当者が全体像から詳細まで段階的に理解できる、更新可能な技術ドキュメントを作成する。

## 依頼形式

```text
文書化 owner/repo [PR作成]
```

`PR作成` がある場合だけ、作業ブランチでドキュメントを作成・更新し、ドラフト Pull Request まで作成する。既定ブランチには直接反映しない。

## 調査

1. `AGENTS.md` / `CLAUDE.md`、README、既存の `docs/`、設定ファイル、主要なエントリーポイント、テスト、CI、デプロイ定義、Open Issue / PR を読む。
2. 実行時の構成、依存関係、外部サービス、永続化、設定値、主要なユーザーフローをコードと設定から追跡する。
3. 既存のドキュメントの配置・言語・用語を優先する。情報が古い、重複する、または欠けている箇所は、実装を正とする。
4. 確認できない意図や将来計画を推測で仕様化しない。推論は「推論」、未確認事項は「未確認」と明記する。

## 作成する内容

既存のドキュメント構造に統合する。構造がない場合は `docs/architecture/` を作り、少なくとも次を用意する。既存の同等資料がある場合は、無意味に複製せず更新・相互リンクする。

- `README.md`（索引）: 文書の目的、対象リビジョン、読み方、各資料へのリンク。
- `system-overview.md`: アプリの目的・対象範囲、実行形態、ディレクトリ／モジュールの地図、責務境界、主要依存関係、起動経路。
- `sequences.md`: 代表的な利用・処理フローを Mermaid のシーケンス図またはフローチャートで示す。初期化、主機能の成功経路、データ保存／取得、外部連携または非同期処理、失敗時の処理を、存在するものだけ取り上げる。
- `implementation-specification.md`: 主要モジュールごとに、責務、入力・出力、重要な型／データモデル、状態遷移、不変条件、エラー処理、他モジュールとの境界、対応する実装ファイルとテストを記録する。

リポジトリの実装に応じて、データスキーマ、設定／環境変数、API契約、認証・認可、ジョブ／キュー、デプロイ／CI、開発・検証手順も追加する。ただし Secret の値、個人情報、内部URL、攻撃に悪用できる詳細は記載しない。

文書は概要から詳細へ進め、コードを大量に転載しない。実装の根拠として具体的なパス・シンボル名・設定名を示し、必要な場合はソース位置へのリンクを使う。Mermaid 図はリポジトリの表示環境で読める簡潔なものにし、図だけに意味を閉じ込めない。

## 品質基準

- 実装済みの機能と、Issue等で検討中の機能を明確に分ける。
- 同じ概念に用語を統一し、略語は初出で説明する。
- 変更時に見直すべき文書と、調査したコミット／ブランチを記録する。
- 既存のリンクと追加リンクを確認し、利用可能ならMarkdown lint・ドキュメントビルド・リンクチェックを実行する。
- コード動作、依存関係、公開API、デプロイ設定は、この依頼だけを理由に変更しない。

## 報告

完了時は日本語で、作成・更新した文書、網羅した範囲、意図的に対象外にした範囲、実行した検証、未確認事項、PR URL（作成した場合）を報告する。
