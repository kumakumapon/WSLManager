# リポジトリ診断プロンプト

このプロンプトは、対象リポジトリの課題と改善機会を調査し、根拠・優先度・完了条件を
備えたGitHub Issueに整理するためのものです。コードや設定を変更せず、診断とIssue作成に
限定します。

## 依頼形式

```text
診断 owner/repo [Issue作成]
```

例:

```text
診断 sj55576/MiniStr
診断 sj55576/MiniStr Issue作成
```

`Issue作成` がない場合は診断結果だけを報告します。明示された場合だけ、重複確認後に
GitHub Issueを作成します。

## 診断手順

1. 対象リポジトリの `AGENTS.md` / `CLAUDE.md`、README、アーキテクチャ、主要コード、
   テスト、依存関係、CI/Workflow、既存のIssue/PRを確認する。
2. 機能、品質、保守性、テスト、アクセシビリティ、性能、運用、ドキュメントの観点から、
   実装または設定で裏付けられる課題・改善機会を抽出する。
3. 各候補に、根拠（関連ファイル・再現条件・不足している検証など）、利用者または開発者への
   影響、推奨する対応、優先度を付ける。推測だけの指摘は候補から除外する。
4. 開いているIssueと最近クローズしたIssueを検索し、同じ原因・対応を扱う候補は既存Issueに
   統合する。関連するが別の完了条件を持つものだけを別Issueにする。
5. `Issue作成` が明示されている場合、優先度と実現性が高い候補だけを、原則5件以内で
   GitHub Issueとして作成する。コード変更、コミット、PR作成は行わない。
6. 作成しなかった候補と理由（重複、根拠不足、スコープ外、既存計画で対応済みなど）も報告する。

## Issueの品質基準

各Issueは、独立して着手判断できるよう次を含める。

```md
## 背景・課題
<現状と、確認できる根拠>

## 影響
<利用者、品質、運用、保守への影響>

## 改善案
<推奨する対応。代替案があれば簡潔に記載>

## 完了条件
- [ ] <確認可能な条件>
- [ ] <必要なテストまたはドキュメント更新>

## 関連情報
- <ファイル、Issue、PR、CIなど>
```

- タイトルは内容が分かる命令形または課題形にし、曖昧な「改善する」「見直す」だけにしない。
- 重大度は根拠に比例させる。低確度の仮説を重大な不具合として登録しない。
- 1件に無関係な改善を詰め込まず、ただし同じ根本原因の細分化もしない。
- Issue Formが有効なリポジトリでは、その必須項目を満たす。

## セキュリティと公開範囲

- 認証情報、Secret、個人情報、実運用データ、攻撃手順、悪用可能な脆弱性の詳細をIssueに書かない。
- セキュリティ上の懸念を見つけた場合は、リポジトリのSecurity Policyまたは非公開の報告経路を
  確認し、公開Issueの作成前に安全な報告先を案内する。
- 依存関係の更新提案は、既存の互換性方針とCI結果を確認してから登録する。

## 報告形式

```md
## 診断結果
- 対象: <owner/repo>
- 確認範囲: <コード・テスト・CI・ドキュメント等>
- 優先度の高い所見: <要約>

## 作成したIssue
- <URL>: <タイトルと要約>
- Issueは作成しなかった（理由）

## 統合・保留した候補
- <候補>: <重複先または保留理由>

## 制約・未確認事項
- <内容>
```
