# CI 失敗修正プロンプト

共通ルール（AI Platform の `prompts/coding-agent-typescript-python.md`、または対象プロジェクトに同期された共通ルール）と、プロジェクト固有の `AGENTS.md` / `CLAUDE.md` をあわせて適用する。

## 入力情報

- 対象リポジトリ、ブランチ、PR（ある場合）
- 失敗した GitHub Actions 実行 URL、Workflow/Job/Step、失敗ログ
- 直近の変更、再現コマンド、対象環境（分かる範囲で）
- 変更可能・変更禁止の範囲

## 作業手順

1. Actions の実行情報とログから、最初に意味のある失敗箇所、失敗した Job/Step、関連ファイルを特定する。ログに含まれる Secret らしい値は表示・報告時にマスクする。
2. ワークフロー定義、依存関係、直近の差分、同等のローカル検証を調査し、根本原因と副次的エラーを区別する。
3. ローカルで安全に再現できる場合は再現し、最小限の修正案を選ぶ。再現不能なら、ログと設定からの根拠・限界を記録する。
4. 特定した原因と修正案を、根拠の十分性・見落とし・実現性の観点でレビューする。Critical または High 相当の懸念（原因未確認のまま修正しようとしている、影響範囲を見誤っているなど）がある場合は、解消するまで手順1〜4を繰り返してから修正に進む。
5. 原因を修正し、必要に応じて回帰テストまたは CI 設定の検証を追加する。
6. 失敗した検証を優先して再実行し、関連する lint、型チェック、テスト、ビルドも実行する。
7. 差分を `prompts/review-pr.md` と同じ観点に加え、CI 設定の権限、Secret の参照、fork PR の安全性、キャッシュの妥当性でレビューする。Critical または High 相当の指摘がある場合は対応し、指摘がなくなるまで手順5〜7を繰り返してから完了とする。

## 完了条件

- 失敗原因、修正内容、根拠が説明できる。
- 修正は失敗を隠すのではなく原因を解消している。
- 失敗していた検証または合理的な代替検証の結果が記録されている。
- PR が必要な場合、再現・修正・検証内容を記載して作成されている。

## 禁止事項

- `continue-on-error`、`if: always()`、skip、テスト削除、チェック無効化だけで成功扱いにしない。
- ログ全文、Secret、トークン、個人情報を転載しない。
- 失敗が未再現・未解決なのに CI が解消したと報告しない。
- 原因未確認の依存更新やワークフロー権限拡大を行わない。

## 報告形式

```md
## CI 失敗の概要
- Workflow / Job / Step: <名前>
- 原因: <根拠を含む要約>

## 修正
- `<path>`: <変更内容と理由>

## 検証
- `<command または Actions URL>`: 成功 / 失敗 / 未実施（理由）

## セキュリティ・リスク
- <Secret、fork PR、互換性など>

## セルフレビュー
- 原因分析: なし / [重大度: Critical / High / Medium / Low] <指摘と対応>
- 差分: なし / [重大度: Critical / High / Medium / Low] <指摘と対応>

## 残課題
- なし / <内容>
```
