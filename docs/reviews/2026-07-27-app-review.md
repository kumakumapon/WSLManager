どう判断したか**を残すことを目的としています。

## 3. 全体評価

### 良い点

- **ロジックの分離方針が明確**。GUI・レジストリ・subprocess に依存しない処理を `wsl_core.py`
  に寄せる方針が徹底されており、6,300 行超のテストがそれを支えている。非 Windows の CI で
  実質的な回帰検知ができているのは、この種の Windows 専用 GUI アプリとしては珍しく良い設計。
- **標準ライブラリのみ**という制約を守り切っており、配布が単純。
- 破壊的操作に対する確認・アトミック書き込み・部分ファイルの後始末など、**データ保護の意識が高い**
  （#6 / #8 / #10 / #14 の対応履歴に表れている）。
- docstring とコメントが「なぜそう書いたか」を説明しており、レビューしやすい。

### 弱い点（今回の起票の背景）

1. **GUI 層にテストの網がかかっていない**。`wsl_core.py` は 4,000 行超のテストで守られている一方、
   `wslmgr.py` (3,908 行) は CI で `import` が通るかを見るだけ。結果として、GUI 側にだけ
   実装の揺らぎ（エラーハンドリングの不統一、ガードの有無）が蓄積している。
2. **同じ処理が箇所ごとに再実装されている**。`subprocess` 実行 + バックグラウンド + UI コールバックの
   定型が 5 クラスに独立して存在し、そのたびに挙動がずれている。1 と互いに原因になっている。
3. **CLI が「GUI の一部の代替」に留まっている**。ログを残さない・終了コードが粗い・変更系に
   機械可読出力がない、と自動化用途で必要なものが揃っていない。
4. **プロジェクト運用基盤が未整備**。バージョン識別子がなく、`pip install` できず、
   PyInstaller ビルドが CI で検証されず、リリースが手作業。コードの品質に対して基盤が追いついていない。
5. **将来の変更に対する備えがない**。永続化フォーマットにスキーマバージョンがなく、
   パーサは認識できない入力を黙って捨てる。どちらも「静かに壊れる」種類の負債。

## 5. 推奨する着手順序

1. **#24 → #25** — 実害のあるバグで、いずれも修正は小さい。まずここ。
2. **#29** — 他の多くの指摘（#26 の一部、#13、#16、GUI のテスト不能状態）の共通の根。
   ここを片付けると後続の修正コストが下がるので、リファクタとしては最優先。
3. **#31 + #32** — 基盤。特に PyInstaller ビルドが CI で検証されていないのは、
   リリース直前に壊れが発覚するリスクを常に抱えている状態。
4. **#30 → #33 / #37** — `wsl_core` の分割時にスキーマバージョンと `TypedDict` を同時に入れると、
   ファイルを触る回数が最小で済む。
5. 残りは機能追加として個別に。

## 6. 意図的に起票しなかったもの

- **既存 issue と重複するもの** — #1〜#22 の内容（i18n、システムトレイ、リソース履歴グラフ、
  スナップショット管理、CLI テスト不足、`messagebox` の `parent` 未指定など）は除外。
- **`_WSL2_FIELDS` の未知キー消失疑い** — 保存時に既存セクションをコピーしてから既知キーのみを
  上書きしていることをコードで確認し、**データ消失ではない**と判断。#40 で「機能不足」として
  扱い、バグとしては起票しなかった。
- **typo・スタイルレベルの指摘** — ruff の管轄であり、issue にする価値が低いと判断。
